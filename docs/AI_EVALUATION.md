# LLM Failure Classification & AI Evaluation

## 1. Role boundary (restated from PRD, load-bearing for this doc)

The LLM classifies and summarizes. It never computes a metric, a statistical test, or a financial value. Every number displayed anywhere in the product traces to `METRICS.md`-defined SQL/Python, never to LLM output. This document covers the one place an LLM genuinely runs at analysis time: **failure-mode classification and evidence extraction**, plus lightweight narrative generation that only interpolates already-computed numbers.

## 2. Failure attribution: hybrid multi-label (supersedes the earlier exclusive taxonomy)

An exclusive single-label classifier was tried first and evaluated twice on a 200-session development benchmark. It forced overlapping failure mechanisms to compete with each other, and it asked an LLM to guess three mechanisms that were actually fully derivable from structured telemetry. The current architecture is a **hybrid multi-label attribution pipeline**: one session can have zero, one, or several of six mechanisms detected simultaneously — they are independent booleans, not branches of one decision.

- **Deterministic** (never guessed by an LLM, recovered from structured data alone — `backend/llm/deterministic_detectors.py`): `retrieval_failure`, `poor_ranking`, `wrong_tool_selection`.
- **Semantic** (require interpreting conversation context — one real LLM call per session, `backend/llm/prompts/semantic_attribution.py`): `unnecessary_clarification`, `wrong_constraint_interpretation`, `unsupported_product_claim`.

`none` is never itself a detected value — it is derived as "no mechanism fired for this session." `other` is deprecated (kept only on the old exclusive-classifier types for historical compatibility) and plays no part in this taxonomy.

## 3. Attribution pipeline

**Input** per session (`SessionContext`, `backend/llm/client.py`): the message transcript, the `agent_actions`/`tool_calls` sequence, `recommendations.satisfies_constraints` flags, and — added for this redesign, since the exclusive classifier had no way to verify a product claim — observable attributes of every shown/recommended product (`ProductEvidence`: category, brand, price, specs, rating, in_stock, use_case_tags; internal-only fields like `margin_pct` are structurally excluded). There is no `sessions.ground_truth_scenario` column and no ground-truth row the pipeline could read by mistake — ground truth is physically absent from the application database (`DATA_MODEL.md` §8).

**Deterministic detectors** are pure functions of `SessionContext`: no LLM call, no randomness. `retrieval_failure` fires when a recommendation was made but no shown candidate satisfies the stated constraints. `poor_ranking` fires when the top pick is itself valid but a materially higher-rated, also-valid candidate sits lower in the shown list. `wrong_tool_selection` fires on two consecutive `search` actions with no filter/clarify step between them.

**The semantic call** is ONE OpenRouter request per session answering all three semantic questions independently, returning `{"unnecessary_clarification": {detected, confidence, evidence_text}, "wrong_constraint_interpretation": {...}, "unsupported_product_claim": {...}}` — never forced to exactly one true value. Reliability configuration (proven across two prior benchmark iterations): OpenRouter's unified `reasoning.effort: "none"` (disables extended thinking, which was silently exhausting the token budget before any JSON was written), a 900-token output budget, strict schema validation (exact keys, confidence in [0,1], non-empty evidence), and bounded retries. A response that's still malformed after retries raises rather than returning a disguised all-false prediction — the pipeline records that session as not-evaluated for this run, never as a normal negative result.

**Provider abstraction**: `backend/llm/client.py`'s `LLMClient` protocol exposes `classify_semantic(context) -> SemanticAttribution` as the current method (`classify_failure` is kept only for historical/backward compatibility with old `failure_labels` rows and tests — nothing in the current pipeline calls it). Two implementations: `OpenRouterLLMClient` (real calls; model configurable via `OPENROUTER_MODEL`, currently a Claude Sonnet model) and `RuleBasedMockClient` (deterministic, CI-safe, zero-API-key fallback). `scripts/run_classification.py --client mock|openrouter` selects one for the batch run.

**Storage**: `session_failure_attributions` — one row per `(session_id, failure_mode)` for each of the six mechanisms, including `detected=false` rows, so "none" is always derivable rather than itself a stored prediction. Each row carries `detector_source` (`deterministic` / `real_llm` / `mock_llm`), `detector_version`, and (for LLM-sourced rows) `provider`/`model`/`prompt_version`. This supersedes the old `failure_labels` table (kept, now permanently empty, for historical compatibility).

**Cost control**: unchanged in spirit — attribution runs once per session at dataset-build/refresh time (`backend/llm/classification_pipeline.py`), not on every page load. The Investigation and AI Quality screens read the cached table.

## 4. Why the semantic call is a real task, not a lookup

Because ground truth exists only in `validation_ground_truth.parquet` (`DATA_MODEL.md` §8) and never in the Postgres database the pipeline and the app both read from, and because message text is generated with lexical/phrasing variation, the semantic call has to infer `unnecessary_clarification`/`wrong_constraint_interpretation`/`unsupported_product_claim` from conversational and product evidence the way a human reviewer would. This is what makes the precision/recall evaluation in §5 meaningful. The three deterministic mechanisms are the opposite case by design: they're moved OUT of the LLM's hands precisely because they're objectively derivable from structured telemetry, so asking a model to guess them would only add noise (confirmed empirically — see the ground-truth audit in the redesign's implementation report, which found these three mechanisms genuinely computed by the generator and simply discarded on export under the old exclusive labeling).

## 5. Evaluating the pipeline

Ground truth for this redesign is independent multi-label truth (`validation_ground_truth.parquet`'s `truth_unnecessary_clarification`, `truth_wrong_constraint_interpretation`, `truth_unsupported_product_claim`, `truth_retrieval_failure`, `truth_poor_ranking`, `truth_wrong_tool_selection` columns — a session can legitimately have more than one `True`), extended from the old single `ground_truth_failure_mode` column specifically for this redesign; the two ground-truth-reading scripts (`tests/validate_ground_truth.py`, `scripts/evaluate_classifier.py`) remain the only permitted readers.

Deterministic detectors are scored as ordinary binary classifiers (precision/recall/F1/support/false-positive/false-negative counts) against their respective `truth_*` column — target F1 ≥0.90 for `retrieval_failure`/`poor_ranking`, ≥0.85 for `wrong_tool_selection`. The semantic call's three outputs are scored independently as three binary classifiers (not collapsed back into one multiclass decision) plus multi-label aggregate metrics — micro/macro F1, exact-match ratio (all three labels correct), Hamming loss — with per-priority-class acceptance bars: `unnecessary_clarification` F1 ≥0.80, `wrong_constraint_interpretation` and `unsupported_product_claim` F1 ≥0.75.

The evaluation methodology itself follows a strict development/held-out split: a 200-session set used to develop and debug the architecture is explicitly archived as development data and never re-presented as an unbiased result; a disjoint 200-session held-out set, constructed and persisted before any LLM call and never resampled after seeing predictions, is the only subset a final number is drawn from.

## 6. Automated evaluation vs. offline task success (relationship to `evaluations` table)

`evaluations.eval_type = offline_task_success` and `constraint_satisfaction` are **not** LLM outputs — they are computed deterministically by checking `recommendations` against `sessions.constraints_json` attribute-by-attribute (e.g., is `price_rub ≤ budget`, is `ram_gb ≥ requested`, is `weight_kg ≤ requested`). This is intentional: the metric that most directly claims "the agent did its job" must be the most auditable one in the system, with no model in the loop. `answer_faithfulness` is the one evaluation type where an LLM judgment is appropriate (checking whether the agent's natural-language claims about a product are supported by that product's actual attributes is a semantic-matching task unsuitable for a rule engine) — this is clearly labeled `evaluator='llm'` in the table and is the only evaluation score in the system with that provenance.

## 7. Narrative generation guardrail

`summarize_finding()` is given a `Finding` object that already contains every number to be mentioned (segment name, deltas, CIs, EC score, dominant failure mode and its share of excess abandonment, dominant trajectory pattern) and is prompted to produce *prose that references these exact figures*, not to compute or estimate new ones. Output is post-validated by regex-extracting any numbers in the LLM's prose and checking they appear in the input `Finding` object; a mismatch is logged and the UI falls back to a template-only sentence (no LLM prose) for that finding. This is the concrete mechanism enforcing "LLM must not be responsible for calculating product metrics" at the narrative layer, where the risk of silent number invention is highest.
